How the source becomes an installable, Perl-free Windows program. This is a **procedure**
rather than a specification, which is why it sits off the reading chain: every other
document answers what chartMaker is and why, and this one answers which tool is run in what
order. [Deployment](deployment.md) describes what the result places on a machine.

The method is arcane and rests on abandonware. All of the source is public, and the recipe
is here so that what is published can be checked against what is built.

## Toolchain

- **Cava Packager 2.0** - scans a Perl/wxPerl application and bundles a private ActivePerl
  5.12 plus wxWidgets 3.0 into Windows executables. The `.cpkgproj` project file is a SQLite
  database. The build is a **GUI operation** - Distribution, then Scan and Build Project;
  `cavaconsole.exe` is a runtime diagnostic console and not a headless builder.
- **Inno Setup 5.5.9** - compiles the generated `innosetup.iss` into the user-facing
  installer executable.
- **ActivePerl 5.12.4** as the development Perl - the same version Cava bundles, so every
  module that works in development is ABI-compatible with the packaged build.

The version of each is recorded in the release log entry it produced, because a packaging
tool is as much a part of a build's provenance as the source is.

## The packaging project is a separate repository

`base_dist/chartMaker` is private and holds the Cava project and the installer
configuration. It carries no source: it `USES` the chartMaker repository, and the two are
tagged together at a release.

Its `.gitignore` ignores everything and re-includes by exception, so the repository holds
the project configuration and nothing regenerable - no built executables, no scan logs, no
release tree. The one lesson worth stating in advance is that **the `.gitignore` has to be
added before the first commit**, because it cannot evict files that are already tracked.

Three files survive that rule: the `.gitignore`, the `.cpkgproj`, and
`cava20/msw/installer.config`.

**Both of the latter two are opaque** - one is a SQLite database with an undocumented
48-column schema, the other a frozen Perl hash - so neither can be read in a diff or checked
in a review. They are therefore not authored by clicking through the packager's tabs but
generated by `_installer/make_cava_project.pl`, which holds every value that defines the
build in one readable place: the version, the two executables and their icons, the forced
includes, the scan paths, and the whole Installer tab. Recreating the project from nothing
is then a command rather than an afternoon.

That script **copies the schema rather than declaring it**, starting from a byte copy of
navMate's project and rewriting its rows. Cava is abandonware carrying a `ddlversion` and no
published DDL, so a hand-written `CREATE TABLE` differing in any detail would be found out
only when the packager refused to open the file.

**Cava owns those files once it has opened them** - it writes build counters and its own
generated values into them - so the generator runs to bring the project into being and not
as part of a build. It refuses to overwrite without `--force` for that reason.

**The icons are the exception to what lives where.** The two `.ico` files are art belonging
to the application, so they are tracked in `_installer/icons`, and `cava20/iconresource.zip`
is built from them by the same script. navMate has this the other way round, with the zip as
the only copy and untracked, which means navMate's icons are in no repository at all.

## What chartMaker requires of a scan

These follow from the source rather than from the packager, so they are knowable before a
build has ever been run.

**The source folder must be on the scan path.** chartMaker loads its own modules by bare
name - `use cm_defs;`, `use dm_set;`, `use w_frame;` - which is a permanent convention, so
the application folder goes on `extrapaths` alongside `C:/base`, which is what resolves
`Pub::`.

**Modules a static scan cannot see have to be forced in.** The test is always the same one:
is the module named anywhere the scanner can read it, or is it resolved by name at run time?

- **`DBD::SQLite`** - `dm_mbtiles` speaks to `DBI`, which loads its driver by name at
  runtime. The MBTiles exporter is the only thing that needs it, and it is exactly the kind
  of dependency a scan misses.
- **`LWP::Protocol::https`** - `Pub::UA` fetches every tile over https, and LWP resolves its
  protocol handler by scheme when the first request is made. This is the costliest one to
  forget: without it a packaged build reaches no tile server at all, while the development
  build it was made from works perfectly.
- **`threads` and `threads::shared`** - used throughout, and the build worker depends on
  them.
- **`JSON` and `JSON::PP`** - regions, sources and the build configuration are all JSON, and
  the application uses both modules directly.

**A conditional `use` is the same problem wearing a disguise**, which is why there is not one
in this application. `use if` hides the module name behind an expression the scanner cannot
evaluate, so the module simply is not found. Where something must be present in one build and
absent in another, the `use` stays unconditional and the RUNTIME is what branches - the
console reader is the only case, and `chartMaker.pm` guards its construction on
`Cava::Packager::IsGUI()` rather than its compilation on anything.

### Shipping a module is not the same as loading it in time

The forced-include list answers *is the file in the bundle*. It says nothing about **when
Perl loads it**, and that second question has its own failure, which is worse because it only
appears in a packaged build and only under threads.

The engine pool is spawned early, deliberately, while the interpreter is still small - an
ithread is a **clone**, and cloning a small one is measurably cheaper. The consequence is that
the workers are cloned before the application has ever made an http request. LWP defers a
great deal of itself to runtime `require`, so the first map load has four threads reaching the
same not-yet-loaded module at the same instant, resolved through Cava's packed virtual
filesystem, which does not survive concurrent readers. What comes back is garbage: the
observed failures were **syntax errors inside module POD**, prose being parsed as code, and a
different module each time. A failed compile leaves `%INC` poisoned, so every later attempt in
that thread dies with `Attempt to reload ... aborted` for the life of the process. Measured:
sixteen tiles dispatched, one fetched, three workers dead for the session.

The fix is to load them before the pool exists, which `dm_fetch` does with a block of
`require` lines for modules it never references. **The list is measured rather than
reasoned** - guessing it cost two rounds, because fixing one module only reveals the next.
`scripts/tool_lwp_preload.pl` snapshots `%INC` around one real fetch and prints what
appeared; an empty report is the passing result, and it should be re-run after any change
to the fetch path or the Perl tree.

The generalisable rule, for the next thing that gets threaded: **anything a worker will use
must be loaded before the worker is spawned**, and in a packaged build that is a correctness
requirement rather than an optimisation.

**`_res` is the resource tree**, and the Leaflet applet in `_res/site` is served from it by
the embedded HTTP server. It bundles wholesale, and `$resource_dir` is what the application
resolves it through in both environments.

Two other things live there and are reached the same way. **`_res/user_data` mirrors the
default data dir**, one folder per tree the application reads:

```
    _res/user_data/sources/*.tsd
    _res/user_data/region_sets/<set>/*.region
```

Its contents are copied into the user's own folders under an existence guard, which is what
makes a shipped source an ordinary editable file. **The layout is the mapping** - in the
ordinary case, where nobody has moved a folder, each destination is identical to its source,
so the copy is the simple thing. It is still a *mapping* rather than a recursive copy,
because every one of those trees is a preference and may point elsewhere; a blind copy into
`$data_dir` would put a shipped source where a user who moved `SOURCES_DIR` would never find
it.

**The installer is no longer the only path to it** - `Help - Restore Shipped Sources and
Examples` performs the same copy at runtime, which is what lets a deleted source come back
without a reinstall and what seeds a development installation. `_res/catalog.json` is the
[tile source catalog](design/catalog.md) and is **not** copied anywhere: it is read where it
lies, because it is application material that has to stay coherent with the code rather than
user data that may be edited.

**The source is packed as plain text rather than masked.** It is public on GitHub, so
masking would obscure nothing and would only make the shipped copy harder to compare against
the published one.

## The two executables

chartMaker packages as two targets from one project: a console-bearing build and a
console-less one, described in [Deployment](deployment.md#the-two-executables). Cava keys an
executable to exactly one entry script, so the second target needs a second file:
`chartMakerGUI.pm` is a fourteen-line shell that requires `chartMaker.pm`. The pairing reads
backwards and is worth stating once - the **windowed** executable is built from the shell,
and the **console** one from the real script.

**Neither executable is elevated.** Both are manifested `asInvoker`, because chartMaker
writes only to the user's own directories. **The installer is elevated**, which is a
different question with a different answer: it writes to Program Files.

The one thing the application asks of the machine that a user will be asked about is the
**listening socket**. It is bound on every interface rather than on the loopback alone -
that is `Pub::HTTP::ServerBase`'s doing and not a decision taken here - so Windows Firewall
will offer its "allow access" prompt the first time an installed build runs. Nothing
depends on the answer: the only client is a browser on the same machine, and a blocked rule
still permits loopback. The installer deliberately adds **no** firewall exception, because
an exception would grant reachability the application has no use for.

## The build

1. Open Cava and confirm the project loaded. It is single-instance, and editing the
   `.cpkgproj` directly requires it closed.
2. Run **Distribution, Scan and Build Project**, then read the scan and build logs. Zero
   warnings is the target; each module a static scan missed becomes another forced include,
   and the build is repeated until the log is clean.
3. Inno compiles the installer from the generated `.iss`. Cava 2.0 emits that file for an
   older Inno than 5.5.9, so `_installer/PreInstallApp.pm` rewrites it first. It does two
   unrelated jobs, and both are unavoidable: it removes the directives 5.5.9 rejects, and it
   injects the things Cava's project format cannot express at all - the seeding of the user's
   data folder, the two scroll-gated agreement pages, and the uninstall question below.
4. Install the result and smoke-test it against a real region set: the map applet in a
   browser, a build to both output formats, and the console executable's output.
5. Commit the packaging repository. That commit is the recipe that produced this executable.

## Cutting a release

The four-repository provenance freeze is specified in
[Deployment](deployment.md#a-release-is-a-tag-in-four-repositories). The order matters more
than the commands do:

1. Commit the source repositories clean.
2. Bump the version and build, which dirties only the packaging repository.
3. Commit the packaging repository.
4. Install the built executable and test it.
5. **Commit nothing further to any of the four**, or the tags will not pin what shipped.
6. Tag all four with `chartMaker<version>` and push the tags, noting each commit.
7. Append the release-log entry and commit it.
8. Create the GitHub Release with the installer as its asset, review it as a draft, publish.
9. **Download the published asset and install it again.** It is the only step that proves
   the uploaded file is intact, and it is the only one that tests what a user will actually
   receive.
